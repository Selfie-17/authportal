# Comprehensive Technical Documentation: Institutional Authentication & Academic Evaluation Portal

---

## 1. Project Title & Abstract

* **Full Project Title**: RGUKT Institutional Authentication, Laboratory Submission Management, and Academic Evaluation Portal (AuthPortal)
* **Author / Architect**: Academic Development Team (B.Tech Computer Science & Engineering)
* **Target Environment**: Multi-campus collegiate university system (RGUKT AP: Nuzvid, RK Valley, Ongole, Srikakulam)
* **Abstract**:
  AuthPortal is an enterprise-grade full-stack academic management solution designed to modernize laboratory assignment submission, continuous evaluation, and feedback distribution in higher educational institutions. Implemented using **Java 21**, **Spring Boot 4.0.8**, **Spring Security 6**, and **React 19**, the system enforces a strict Zero-Trust institutional identity framework via Google OAuth 2.0 / OpenID Connect and local credential management. The system introduces server-side institutional email parsing to eliminate client-side role forgery, an ephemeral exchange code protocol to prevent token leakage in OAuth redirects, deep magic-byte validation to neutralize disguised executable payloads, and a dual-engine mail delivery subsystem that overcomes cloud SMTP port filtering via direct Gmail REST API (v1) integration over HTTPS Port 443. The system supports multi-provider evaluation ingestion (Google Gemini, Ollama), inline PDF rendering via PDF.js, and pluggable cloud storage using Backblaze B2 S3 API. The entire system is validated with 121 automated unit and integration tests.

## 2. Introduction & Background

Engineering education requires continuous laboratory practice where students write code, conduct experiments, and submit technical lab reports weekly over a 12-week semester. At institutions like the Rajiv Gandhi University of Knowledge Technologies (RGUKT), thousands of students across multiple campuses take intensive programming labs (such as C Programming, Data Structures, and Operating Systems).

Historically, academic institutions have managed this workflow using heterogeneous, unintegrated tools:
- Submissions collected via generic Google Forms or shared Drive folders.
- Evaluation rubrics recorded in disparate offline Excel spreadsheets.
- Student feedback communicated informally or not at all.
- Distribution of evaluated rubrics conducted through manual, error-prone email forwarding.

This manual paradigm creates administrative friction, data fragmentation, risk of malicious file uploads, lack of submission versioning, and zero audit trails. AuthPortal was developed to unify these disconnected stages into a secure, cohesive web platform.

## 3. Problem Statement

Collegiate laboratory administration suffers from five critical systemic deficiencies:
1. **Identity & Privilege Escalation Risks**: Public registration portals that allow users to select their own roles (`STUDENT`, `TEACHER`, `ADMIN`) risk severe privilege escalation. Furthermore, students frequently use personal accounts (e.g., `@gmail.com`) rather than institutional credentials, impeding identity verification.
2. **Security Hazards in Unrestricted File Uploads**: Simple file extension validation (checking for `.c` or `.pdf`) is inadequate. Malicious or inquisitive students can disguise compiled binaries (`.exe`, ELF, Mach-O) by simply renaming the file extension, exposing institutional evaluation infrastructure to malware.
3. **Token Leakage in OAuth Redirection**: Standard OAuth2 single-page application (SPA) patterns frequently pass JWTs directly in URL hash fragments or query parameters (`https://frontend/?token=ey...`). These tokens become permanently logged in browser history, HTTP Referer headers, proxy server logs, and web analytics.
4. **Cloud Network Restrictions on Outbound Mail**: Modern cloud platforms (e.g., Render Free Tier, AWS EC2 default security groups) strictly block outbound traffic on standard SMTP ports (25, 465, and 587) to prevent spam. This renders standard JavaMailSender configurations inoperable in budget-constrained institutional hosting environments.
5. **Evaluation Inaccessibility and Feedback Latency**: Evaluated lab reports generated by automated grading rubrics or AI tools (Gemini, Ollama) remain siloed on instructor machines, depriving students of timely, actionable feedback prior to subsequent lab sessions.

The motivation behind AuthPortal is threefold:
- **Institutional Governance**: Enforce strict academic identity verification by anchoring user permissions to official RGUKT institutional email structures (`@rguktn.ac.in`, `@rguktrkv.ac.in`, `@rguktong.ac.in`, `@rguktsklm.ac.in`, and `@rgukt.in`).

- **Pedagogical Feedback Optimization**: Provide an interactive, high-speed evaluation spreadsheet grid with inline PDF viewing and an automated batch email dispatcher so students receive formatted evaluation reports instantly.

## 8. Functional Requirements

### 8.1 Module 1: Authentication & Authorization (All Roles)
- **FR-01**: The system shall authenticate users via local credentials (email/password) hashed using BCrypt.
- **FR-02**: The system shall authenticate users via Google OAuth 2.0 / OpenID Connect.
- **FR-03**: The system shall strictly restrict registration and login to institutional domains: `rguktn.ac.in`, `rguktrkv.ac.in`, `rguktong.ac.in`, `rguktsklm.ac.in`, and `rgukt.in`.
- **FR-04**: The system shall automatically resolve user roles server-side:
  - Emails matching `^[A-Za-z]\d{6}@...` are assigned `STUDENT`.
  - Non-student institutional emails matching `TEACHER_ALLOWED_EMAILS` are assigned `TEACHER`.
  - Whitelisted emails matching `GOOGLE_ADMIN_EMAILS` receive `ADMIN` privileges.
- **FR-05**: The system shall implement an ephemeral single-use exchange code pattern for OAuth redirects, returning the JWT via a secure POST request.
- **FR-06**: The system shall issue stateless HMAC-SHA256 signed JWT tokens valid for 24 hours (configurable).
- **FR-07**: The system shall link local accounts to Google identities safely when email addresses match without downgrading roles.

### 8.2 Module 2: Student Laboratory Submission (Student Role)
- **FR-08**: The system shall pre-fill the student's ID from their authenticated institutional email address.
- **FR-09**: The system shall accept laboratory submissions comprising one or more `.c` source files and `.pdf` reports for a designated Week (1–12), Academic Year (E1–E4), and Section (1–6).
- **FR-10**: The system shall reject files exceeding 20MB individually or 500MB per aggregate request.
- **FR-11**: The system shall inspect file headers and reject Windows PE (`MZ`), Linux ELF (`\x7FELF`), and Mach-O binary executables.
- **FR-12**: The system shall detect duplicate submissions for the same (Week, Year, Section), increment the revision counter (`v1 -> v2`), and clean up older files.
- **FR-13**: The system shall allow students to delete their own submissions, purging both database records and physical storage objects.
- **FR-14**: The system shall display submission history allowing students to review and download submitted files.

### 8.3 Module 3: Teacher Evaluation & Lab Oversight (Teacher & Admin Roles)
- **FR-15**: The system shall display a dynamic spreadsheet grid aggregating students (rows) and evaluation weeks (columns).
- **FR-16**: The system shall display criterion-level scores (*Objective*, *Problem Understanding*, *Logic/Approach*, *Variables*, *Observation*, *Total*, *Final*).
- **FR-17**: The system shall allow teachers to view the student's uploaded PDF lab report inline in the browser via PDF.js.
- **FR-18**: The system shall render Markdown observation reports and parse LaTeX mathematical formulas using KaTeX.
- **FR-19**: The system shall allow teachers to record qualitative feedback comments, toggle review status, and update awarded marks.
- **FR-20**: The system shall generate on-the-fly streaming ZIP archives containing all submissions for a selected week and section organized by student ID.
- **FR-21**: The system shall ingest evaluation reports uploaded in JSON format or parsed from ZIP archives.

### 8.4 Module 4: Email Notification & Batch Reporting (Teacher & Admin Roles)
- **FR-22**: The system shall support sending individual student evaluation reports via email.
- **FR-23**: The system shall support bulk batch email distribution filtered by Week, Academic Year, Branch, and Section.
- **FR-24**: The system shall provide an interactive preview of candidate recipients prior to launching batch delivery.
- **FR-25**: The system shall execute batch email dispatch asynchronously to prevent HTTP request timeouts.
- **FR-26**: The system shall track the delivery status (`PENDING`, `SENT`, `FAILED`) of every individual recipient in an email batch.
- **FR-27**: The system shall allow teachers to retry failed deliveries individually or in bulk.
- **FR-28**: The system shall provide a safe testing mode (`targetOverrideEmail`) to direct batch test emails to instructor inboxes.
- **FR-29**: The system shall deliver emails via **Gmail SMTP** when running locally or on unblocked hosts.
- **FR-30**: The system shall deliver emails via **Google Gmail REST API (v1)** over HTTPS Port 443 when deployed in cloud environments blocking outbound SMTP.

### 8.5 Module 5: Administrative Console (Admin Role)
- **FR-31**: The system shall present real-time KPI metrics: Total Users, Students, Teachers, Admins, and Submissions.
- **FR-32**: The system shall list all registered users with search and role filtering.
- **FR-33**: The system shall allow administrators to provision new users with designated roles.
- **FR-34**: The system shall allow administrators to update user roles while preventing demotion of the final remaining administrator.
- **FR-35**: The system shall allow administrators to enable or disable accounts while preventing administrators from disabling their own accounts.
- **FR-36**: The system shall allow administrators to view and delete any submission across the institution.

## 9. Non-Functional Requirements

### 9.1 Security & Protection
- **NFR-01**: Passwords must be hashed using BCrypt with a secure work factor. Plaintext passwords must never be logged or stored.
- **NFR-02**: All private endpoints must require valid JWT authentication in the `Authorization: Bearer <token>` header.
- **NFR-03**: Role-based access control must be enforced at both the HTTP security filter chain and the service method level using `@PreAuthorize`.
- **NFR-04**: CORS configuration must restrict incoming origins strictly to approved frontend URLs.
- **NFR-05**: Ephemeral OAuth exchange codes must be single-use and automatically expire within 60 seconds.
- **NFR-06**: Direct file storage keys must never be accepted from client request parameters to prevent Arbitrary File Read and Insecure Direct Object Reference (IDOR) vulnerabilities.

### 9.2 Performance & Responsiveness
- **NFR-07**: REST API endpoints (excluding file streaming) must respond within 200 milliseconds under standard load.
- **NFR-08**: File downloads and ZIP archives must stream directly to the client via `StreamingResponseBody` without pre-buffering entire payloads into server RAM.
- **NFR-09**: Client-side evaluation grid data must leverage Stale-While-Revalidate (SWR) in-memory caching to provide instantaneous rendering upon tab switching.

### 9.3 Scalability & Reliability
- **NFR-10**: The backend must remain completely stateless to facilitate horizontal scaling behind load balancers.
- **NFR-11**: Cloud file storage must utilize Backblaze B2 S3-compatible object storage to provide virtually limitless scalability for student files.
- **NFR-12**: Database schema alterations must be managed strictly through idempotent, versioned Flyway migration scripts.

### 9.4 Maintainability & Code Quality
- **NFR-13**: Codebase must adhere to standard Spring layered architecture (Controller -> Service -> Repository -> Entity).
- **NFR-14**: Comprehensive automated test suite must maintain high branch coverage across security filters, services, and controllers.

## 11. System Architecture

AuthPortal follows a decoupled, three-tier enterprise architecture:
1. **Presentation Tier (React 19 SPA)**: Runs entirely in the client browser, handling state, routing, file chunking, and rendering.
2. **Application Tier (Spring Boot REST Backend)**: Handles authentication, business logic, validation, security filtering, and cloud integration.
3. **Data Tier (MySQL Database & Backblaze B2 Object Storage)**: Persists relational state, metadata, user identities, and raw laboratory submission files.

```text
[ Browser / React 19 Client ]
         |
         | HTTPS (JSON / REST API / Multipart Uploads)
         v
[ Spring Boot 4 REST Backend ]
   +-- JwtAuthenticationFilter
   +-- SecurityFilterChain (RBAC)
   +-- REST Controllers (Auth, Submission, Teacher, Admin, Email)
   +-- Business Services (SubmissionService, EvaluationService, EmailBatchService)
   +-- Storage Abstraction Layer (LocalStorageService / BackblazeB2StorageService)
         |                              |                           |
         | JDBC (HikariCP)              | S3 API (Port 443)         | HTTPS (Port 443) / SMTP (587)
         v                              v                           v
[ MySQL 8.0 Database ]         [ Backblaze B2 Storage ]     [ Google Gmail REST API / SMTP ]
```

## 12. Frontend Architecture

The frontend is structured cleanly inside `frontend/src/`:
- **Routing & Route Protection (`App.jsx`)**: Implements `<ProtectedRoute allowedRoles={[...]}>` which inspects user authentication status and role permissions. If an unauthenticated user attempts access, they are redirected to `/login`; if an authenticated user attempts access to an unauthorized role view, they are redirected to their primary portal.
- **Authentication Service (`services/authService.js`)**: Encapsulates token persistence in `localStorage`, user session deserialization, and header generation (`Authorization: Bearer <token>`).
- **Client-Side Caching Subsystem (`services/cache/`)**:
  - `gridCache.js`: In-memory cache for evaluation table data supporting Stale-While-Revalidate (SWR) fetching.
  - `pdfCache.js`: In-memory cache for PDF blob representations preventing redundant network downloads.
  - `reportCache.js`: Cache for parsed Markdown and JSON evaluation reports.
- **Component Design System**:
  - Modular UI components in `components/` (`Navbar.jsx`, `FileUploadZone.jsx`, `TeacherReportView.jsx`).
  - Specialized administrative modules in `components/admin/` (`AdminStatCard.jsx`, `Pagination.jsx`, `RoleBadge.jsx`, `UserActionsMenu.jsx`).
  - Teacher evaluation components in `components/teacher/` (`StudentScoreTable.jsx`, `UploadedPdfViewer.jsx`, `EmailReportModal.jsx`, `MarkdownReportRenderer.jsx`).
- **Mathematical Typography (`utils/mathRenderer.jsx`)**: Integrates KaTeX to parse LaTeX expressions delimited by `$...$` or `$$...$$` embedded within laboratory evaluation reports.

## 13. Backend Architecture

The backend is built inside `authportal/src/main/java/com/selva/authportal/`:
- **Configuration Layer (`config/`)**:
  - `SecurityConfig.java`: Configures stateless `SecurityFilterChain`, CORS rules, exception entry points, and OAuth2 login filters.
  - `BackblazeStorageProperties.java`: Binds application configuration (`app.storage.backblaze.*`) to strongly-typed properties.
  - `AsyncConfig.java`: Enables asynchronous task execution for non-blocking email batch dispatching.
  - `PasswordEncoderConfig.java`: Exposes BCrypt password encoder bean.
- **Security & OAuth Layer (`security/`)**:
  - `JwtAuthenticationFilter.java`: Intercepts incoming requests, validates Bearer tokens, extracts claims, and populates Spring Security's `SecurityContextHolder`.
  - `JwtService.java`: Generates, signs, and parses HMAC-SHA256 JWT tokens.
  - `OAuth2ExchangeCodeStore.java`: Thread-safe concurrent storage for single-use OAuth exchange codes with TTL eviction.
  - `OAuth2AuthenticationSuccessHandler.java`: Intercepts successful Google login, resolves user role, generates an exchange code, and redirects to frontend.
- **Controller Layer (`controller/`)**: Exposes REST endpoints, validates DTO inputs with `@Valid`, and delegates business operations to services.
- **Service Layer (`service/`)**: Contains all core transactional business logic, file validations, storage management, and email processing.
- **Data Access Layer (`repository/` & `model/`)**: Defines JPA entities and Spring Data repositories using `JpaSpecificationExecutor` for dynamic multi-criteria filtering.

### Table Breakdown
1. **`users`**: Stores user authentication records, hashed passwords, institutional email, assigned role (`STUDENT`, `TEACHER`, `ADMIN`), academic metadata (`branch`, `academic_year`, `section`), auth provider (`LOCAL`, `GOOGLE`), and account status.
2. **`submissions`**: Represents an assignment submission for a specific student, week, year level, and section. Contains unique constraint `uq_user_week_year_sec` and revision version counter.
3. **`submission_files`**: Stores individual files attached to a submission. Records `original_filename`, `stored_filename`, `file_type` (`C_SOURCE` or `PDF_REPORT`), `file_size_bytes`, and provider-neutral `storage_key`.
4. **`student_evaluations`**: Records quantitative criterion scores, final grades, and raw JSON evaluation output. Unique constraint `uq_eval_student_week_provider` allows storing both Gemini and Ollama evaluations for the same student and week.
5. **`teacher_feedbacks`**: Stores manual qualitative comments and review status toggled by faculty members, preserved independently of automated re-evaluations.
6. **`email_batches`**: Tracks aggregate batch email campaigns dispatched to student cohorts, recording counts of total, sent, failed, and pending recipients.
7. **`email_batch_recipients`**: Tracks individual delivery state (`PENDING`, `SENT`, `FAILED`), Gmail message ID, error logs, and retry attempts for every recipient in a batch.
8. **`email_automation_configs`**: Stores automated email settings, trigger conditions, connected Gmail address, and encrypted OAuth2 refresh tokens for the Gmail REST API.

## 15. REST API Documentation

### 15.1 Authentication API (`/api/auth`)
- `POST /api/auth/register` (Public): Registers a student or teacher account with institutional email verification.
- `POST /api/auth/login` (Public): Authenticates via email/password, returning JWT and user profile.
- `POST /api/auth/oauth2/exchange` (Public): Exchanges a 60-second single-use OAuth authorization code for a JWT token.
- `GET /api/auth/me` (Authenticated): Retrieves profile information for the authenticated token bearer.
- `POST /api/auth/logout` (Authenticated): Client-side logout acknowledgement.

### 15.2 User Profile API (`/api/profile`)
- `GET /api/profile` (Authenticated): Returns current user profile details.
- `PUT /api/profile` (Authenticated): Updates personal details (e.g., name).
- `POST /api/profile/change-password` (Authenticated): Updates password after validating current password.

### 15.3 Student Submission API (`/api/submissions`)
- `GET /api/submissions/default-student-id` (Student, Admin): Returns auto-derived student ID and profile defaults.
- `POST /api/submissions` (Student, Admin, `multipart/form-data`): Uploads files for a lab submission.
- `GET /api/submissions/my` (Student, Admin): Lists submissions belonging to the authenticated student.

## 16. Detailed Module Breakdown

### 16.1 Authentication & Role Resolution Module
Implemented across `AuthController.java`, `AuthService.java`, `EmailRoleResolver.java`, and `CustomOAuth2UserService.java`.
- **Functionality**: Manages user registration, login, institutional email verification, role assignment, and OAuth2 integration.
- **Workflow**: When a user registers or logs in with Google, `EmailRoleResolver` extracts the email domain. If the domain is not in `app.auth.institutional-domains`, access is immediately rejected. If the email matches the student regex pattern, the user is assigned `ROLE_STUDENT`. If the email is listed in `TEACHER_ALLOWED_EMAILS`, they receive `ROLE_TEACHER`. Whitelisted emails receive `ROLE_ADMIN`.

### 16.2 Laboratory Submission & Inspection Module
Implemented across `SubmissionController.java`, `SubmissionService.java`, and `SubmissionPathUtils.java`.
- **Functionality**: Accepts student laboratory files, inspects byte content, creates database records, and writes files to storage.
- **Security Check**: Reads initial bytes of uploaded files. Rejects files starting with `MZ` (Windows PE header `0x4D, 0x5A`), `\x7FELF` (Linux executable `0x7F, 0x45, 0x4C, 0x46`), or Mach-O binary headers. Validates `%PDF-` signature for PDF reports.

### 16.3 Cloud Object Storage Module
Implemented across `StorageService.java`, `LocalStorageService.java`, and `BackblazeB2StorageService.java`.
- **Functionality**: Provides a unified storage interface (`storeFile`, `loadFile`, `deleteFile`, `deleteDirectory`).
- **Cloud Integration**: When configured for Backblaze B2, connects via AWS SDK for Java v2 to an S3-compatible bucket. Directly streams files via `PutObjectRequest` and `ResponseInputStream` without staging files on the server's local disk.

### 16.4 Teacher Evaluation Grid & PDF Viewer Module
Implemented across `TeacherEvaluationController.java`, `EvaluationService.java`, and frontend components.
- **Functionality**: Aggregates all uploaded student evaluations and formats them into a spreadsheet table with dynamic week columns.
- **Inline Inspection**: When a teacher clicks on an evaluation cell, the frontend fetches the student's submitted PDF via `/api/teacher/evaluations/pdf` and renders it directly using PDF.js alongside the Markdown assessment and qualitative teacher feedback form.

### 16.5 Dual-Engine Email Reporting Module
Implemented across `EmailReportController.java`, `EmailBatchService.java`, `ReportEmailService.java`, `GmailEmailService.java`, and `GmailRestApiService.java`.
- **Functionality**: Delivers formatted academic evaluation reports to student inboxes.
- **Dual Engine Logic**: Inspects `GmailRestApiService.isConfigured()`. If an OAuth2 refresh token is present, dispatches emails via HTTPS POST to `https://gmail.googleapis.com/gmail/v1/users/me/messages/send` (Port 443), completely bypassing cloud SMTP port blocks. If not configured, falls back to standard Gmail SMTP on port 587.

### 16.6 Administrative Console Module
Implemented across `AdminController.java`, `AdminService.java`, and `AdminDashboardPage.jsx`.
- **Functionality**: Provides institutional oversight, user account management, and aggregate metric reporting.
- **Safety Guards**: Prevents demoting the last remaining active administrator and prevents administrators from disabling their own accounts.

## 17. Important Algorithms & Business Logic

### 17.1 Institutional Email & Student ID Parsing
Implemented in `EmailRoleResolver.java`:

```java
// Institutional domain validation
boolean isValidDomain = institutionalDomains.stream()
    .anyMatch(domain -> email.toLowerCase().endsWith("@" + domain.toLowerCase()));

// Student ID derivation regex

if (studentPattern.matcher(email).matches()) {
    return Role.STUDENT;
}
```

### 17.2 Executable Header (Magic Byte) Inspection
Implemented in `SubmissionService.java`:
```java
private void validateFileContent(MultipartFile file, SubmissionFileType expectedType) throws IOException {
    byte[] header = new byte[8];
    try (InputStream is = file.getInputStream()) {
        int bytesRead = is.read(header);
        if (bytesRead < 4) return;
    }

    // Windows PE check (MZ)
    if (header[0] == 0x4D && header[1] == 0x5A) {
        throw new InvalidFileException("Disguised Windows executable binary detected.");
    }
    // Linux ELF check (\x7FELF)
    if (header[0] == 0x7F && header[1] == 0x45 && header[2] == 0x4C && header[3] == 0x46) {
        throw new InvalidFileException("Disguised Linux executable binary detected.");
    }
    // PDF Magic Byte check (%PDF-)
    if (expectedType == SubmissionFileType.PDF_REPORT) {
        String magic = new String(header, 0, 5, StandardCharsets.US_ASCII);
        if (!magic.startsWith("%PDF-")) {
            throw new InvalidFileException("Corrupt or invalid PDF document format.");
        }
    }
}
```

### 17.3 Zero-JWT Ephemeral Exchange Code Store
Implemented in `OAuth2ExchangeCodeStore.java`:
- Generates a cryptographically secure random token (32 bytes Base64URL-encoded).
- Stores token in a `ConcurrentHashMap` mapped to user identity with a timestamp.
- On client exchange (`POST /api/auth/oauth2/exchange`), the code is atomically retrieved and removed (**single-use**).
- Verifies elapsed time is less than 60,000 milliseconds (TTL). If expired or invalid, throws `UnauthorizedException`.

### 17.4 Direct On-The-Fly ZIP Streaming
Implemented in `ZipArchiveService.java`:
- Accepts week, year, and section parameters.
- Fetches all matching submissions and files from the database.
- Streams output directly into HTTP response via `StreamingResponseBody` wrapped around `ZipOutputStream`.
- As each file is read from Backblaze B2 or local disk, bytes are copied directly to the `ZipOutputStream` without creating intermediate ZIP files on the server's filesystem.

## 18. Authentication & Security Architecture

1. **Password Encryption**: Employs BCrypt hashing algorithm with automated salt generation.
2. **Stateless JWT**: JJWT signs tokens using HMAC-SHA256 (`Keys.hmacShaKeyFor(secret.getBytes())`). Token claims contain subject (email), user ID, and granted authorities (`ROLE_STUDENT`, `ROLE_TEACHER`, `ROLE_ADMIN`).
3. **Defense Against Privilege Escalation**:
   - Local registration DTO (`RegisterRequest`) contains only `name`, `email`, and `password`. The client cannot pass a role.
   - The role is computed server-side by `EmailRoleResolver`.
4. **CORS Security**: Strict allowed origins configured in `SecurityConfig.java` preventing unauthorized cross-origin requests.
5. **CSRF Protection**: Because the application uses stateless Bearer JWT tokens stored in browser client memory/localStorage rather than ambient session cookies, CSRF is disabled in alignment with modern stateless API security practices.

## 22. Key Engineering Challenges & Solutions

### Challenge 1: Outbound SMTP Blocking on Cloud Free Tiers
- **Issue**: Deploying on Render resulted in immediate connection timeouts when sending emails because Render blocks ports 25, 465, and 587 on its free tier to mitigate spam.
- **Solution**: Engineered `GmailRestApiService.java`. The system connects to Google's OAuth2 token endpoint to obtain a short-lived access token and sends RFC 2822 MIME messages directly via the Gmail REST API (v1) over standard HTTPS Port 443, completely bypassing network firewall blocks.

### Challenge 2: Ephemeral Filesystem Data Loss
- **Issue**: Standard PaaS hosting instances (Render, Heroku) feature ephemeral filesystems. Any student file saved to local disk was wiped whenever the container restarted.
- **Solution**: Implemented `BackblazeB2StorageService.java` using the AWS SDK for Java v2. Files are streamed directly to Backblaze B2 S3 buckets with deterministic storage keys (`submissions/week-{w}/sec-{s}/{studentId}/{filename}`).

### Challenge 3: Insecure Disguised Executable Uploads
- **Issue**: Students could rename compiled `.exe` or ELF binaries to `.c` or `.pdf` to bypass frontend extension filters.
- **Solution**: Implemented magic-byte header inspection in `SubmissionService.java`, inspecting initial file bytes to block Windows PE (`MZ`), Linux ELF (`\x7FELF`), and Mach-O binaries.

### Challenge 4: OAuth Token Exposure in Frontend Redirection
- **Issue**: Traditional SPA OAuth redirects place the JWT in the URL hash or query string (`?token=ey...`), exposing it in browser history, proxy logs, and referrer headers.
- **Solution**: Implemented `OAuth2ExchangeCodeStore.java`. On successful OAuth login, the backend issues an ephemeral 60-second single-use exchange code in the URL. The React frontend immediately exchanges this code for the JWT via a secure POST request.
